# TALA Engine Specification

**Document:** TALA_ENGINE_SPEC.md\
**Specification Version:** 1.0\
**Engine Version:** RC3.0.0 (Baseline)\
**Status:** Draft

------------------------------------------------------------------------

# 1. Purpose

The TALA Engine is a modular schema synchronization engine responsible
for analyzing, planning, validating, and executing database schema
synchronization between two database connections.

The engine is designed to be reusable by TalaKlase and future
applications.

------------------------------------------------------------------------

# 2. Design Principles

-   Single Responsibility Principle
-   Handler-based execution
-   Deterministic execution order
-   Database agnostic (PDO)
-   Extensible through handlers
-   Safe before fast
-   Every operation must be executable and reportable

------------------------------------------------------------------------

# 3. Engine Pipeline

``` text
Source Database
        │
        ▼
SchemaInspector
        │
        ▼
SchemaMerger
        │
        ▼
MergeValidator
        │
        ▼
ExecutionPlanBuilder
        │
        ▼
SchemaExecutor
        │
        ▼
Operation Handler
        │
        ▼
Destination Database
```

------------------------------------------------------------------------

# 4. Operation Contract

Every operation generated by the engine SHALL follow this structure.

``` php
[
    'id' => 'OP-000001',

    'operation' => 'create_table',

    'target_type' => 'table',

    'target' => 'student',

    'priority' => 100,

    'details' => [
        // operation-specific metadata
    ],

    'sql' => 'CREATE TABLE ...',

    'metadata' => [
        'spec_version' => '1.0',
        'engine_version' => 'RC3.0.0',
        'generated_by' => 'ExecutionPlanBuilder',
        'generated_at' => 'YYYY-MM-DD HH:MM:SS'
    ]
]
```

## Required Fields

  Field         Description
  ------------- -----------------------------------------
  id            Unique operation identifier
  operation     Operation type
  target_type   Table, column, index, foreign_key, etc.
  target        Target object name
  priority      Execution order
  details       Operation-specific metadata
  sql           SQL to execute
  metadata      Generation information

## Tables

-   create_table
-   drop_table

## Columns

-   add_column

-   drop_column

## Indexes

-   create_index
-   drop_index

## Foreign Keys

-   create_foreign_key
-   drop_foreign_key

# 6. Handler Contract

Each handler is responsible for exactly one operation type.

``` php
interface OperationHandlerInterface
{
    public function execute(array $operation): array;

    public static function operation(): string;
}
```

Rules:

-   One handler = one operation
-   No business logic inside SchemaExecutor
-   Handlers execute SQL only
-   Handlers return standardized results

------------------------------------------------------------------------

# 7. Result Contract

Every handler SHALL return:

``` php
[
    'operation_id' => 'OP-000001',

    'status' => 'executed',

    'reason' => null,

    'error' => null,

    'started_at' => '',

    'finished_at' => '',

    'duration_ms' => 0
]
```

## Status Values

-   executed
-   skipped
-   failed

------------------------------------------------------------------------

# 8. Execution Report

SchemaExecutor SHALL return:

``` php
[
    'status' => true,

    'summary' => [
        'executed' => 0,
        'failed' => 0,
        'skipped' => 0
    ],

    'operations' => [
        // handler results
    ]
]
```

# 9. Priority Rules

    Priority Object
  ---------- --------------
         100 Tables
         200 Columns
         300 Indexes
         400 Foreign Keys
         500 Constraints

ExecutionPlanBuilder is responsible for assigning priorities.

------------------------------------------------------------------------

# 10. Responsibilities

## SchemaInspector

-   Analyze source and destination schemas
-   Produce schema differences

## SchemaMerger

-   Convert differences into logical merge operations

## MergeValidator

-   Validate merge operations

## ExecutionPlanBuilder

-   Produce executable operations
-   Assign IDs
-   Assign priorities
-   Generate SQL

## SchemaExecutor

-   Dispatch operations
-   Collect execution reports
-   Never generate SQL

## Operation Handlers

-   Execute SQL
-   Handle operation-specific behavior
-   Return standardized results

------------------------------------------------------------------------

# 11. Non-Goals

The engine SHALL NOT:

-   Build SQL inside SchemaExecutor
-   Mix planning with execution
-   Execute unordered operations
-   Hide execution failures
-   Modify operations at runtime

------------------------------------------------------------------------

# 12. Versioning

This specification follows semantic versioning.

-   1.x --- Backward-compatible additions
-   2.x --- Breaking contract changes

Execution plans SHOULD include the specification version they were
generated with.
